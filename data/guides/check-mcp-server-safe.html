A listing is not a review

The official MCP documentation on local server security puts this plainly: a listing on a registry is not an endorsement. Docker Hub, npm, PyPI and GitHub will host almost anything. A familiar name, a high star count, or a page on a directory (this one included) does not mean the code is safe, current, or what it claims to be.

PickAPlugin does not test or audit plugins or MCP servers. Descriptions and install commands come from each project's README or from the maker. We show useful signals (last commit, archived or not, license, the install line) so you can do the next part yourself. This guide is that next part, based on official MCP, Claude, Cursor and Codex docs, not on a security lab we don't run.

If you're vetting a ChatGPT or Codex plugin (a marketplace package that may include skills, hooks and an MCP server), start with the plugin checklist. This page is about the MCP server itself, including ones you add by hand in Claude Desktop, Cursor or Codex. For the install steps, see how to install an MCP server in those three apps.

What you're actually trusting

Official local-server docs make a distinction that the word "plugin" tends to hide.

A local stdio server is an ordinary process your app starts as you. It inherits a lot of what your account can do. The protocol does not sandbox it. In practice that process can read files your user can read (SSH keys, cloud creds, browser profiles, the rest of your home directory), see environment variables you pass to it, and open outbound network connections. The official guide's short version: your real security decisions happen before launch, in what you install and how you run it. The stdio transport is not a fence.

A remote HTTP server is a different trade. The code isn't running as you, but your agent is sending tool calls and often file contents, prompts or API data to a machine you don't control. You're trusting the operator with whatever the model decides to send, and with whatever tools that server exposes (some of them write, delete, post or pay, not just read).

Trust also stacks. Every server you enable shares the model's context, so a sloppy or hostile server can influence how the agent uses the tools of the others. Official advice is to keep the roster small, and to remove servers you no longer use.

A practical checklist

1. Know what's already on the machine

Before you add anything, open the config you already have and read it. Claude Desktop: claude_desktop_config.json, plus the Extensions page. Cursor: Customize → MCPs, and the two mcp.json files (~/.cursor/mcp.json and .cursor/mcp.json). Codex: codex mcp list, or ~/.codex/config.toml. Official MCP guidance starts here: remove servers you don't use, and make sure you can say where each remaining one came from and which version you're running.

2. Identify the publisher

Can you tie the package to a source repository and a real maintainer or organization? Does the repo show recent, plausible activity, or did it go quiet for a year and then suddenly publish a new release? On PickAPlugin, the listing links to the repo when we have one, shows the last commit date we last fetched, and marks archived projects. Those are starting clues, not a verdict. Open the repo. Check the publisher's other work. Be suspicious of a brand-new package that mimics a well-known server's name.

3. Check the exact package name

Typosquatting is cheap. Confirm the npm, PyPI or Docker name in the install command is the one the documentation actually refers to, not a lookalike with a swapped character or an extra hyphen. Read the command letter by letter against the official README. If a blog post, a chat reply or a directory listing (ours included) disagrees with the repo, trust the repo and the official registry page.

Example: official MCP docs install the filesystem server as @modelcontextprotocol/server-filesystem. A package named @modelcontextprotocal/server-filesystem or mcp-filesystem-server is not that package, no matter how similar the README looks.

4. Pin the version

The official local-server guide recommends installing a specific version rather than latest, so a compromised future release doesn't land on your machine through an automatic pull. That matters a lot for one-liners like npx -y some-package@latest, which many READMEs still use because they're convenient.

There's a second catch, also from those docs: pinning the top-level package with npx or uvx does not freeze transitive dependencies. Those are often resolved at install time, which is a common place for a compromised dependency to sneak in. Pinning a container image by digest (image@sha256:…) freezes the whole tree. If a project publishes a signed image or build attestations, that's a stronger artifact than an unpinned npx -y line.

On our listings, if you see @latest (for example the local Codex install on IPGeolocation.io MCP Server), treat that as the project's convenient default, then pin a version from npm or the repo's releases once you're happy with it.

5. Read the actual command

One-click and CLI installers should show you the command before it runs. Official MCP client guidance (SEP-1024) expects that. Read it. You're looking for:

  • A surprising download host, or a curl-piped-to-shell installer you weren't expecting.
  • Arguments that grant filesystem paths, Docker sockets, or cloud roles you didn't intend.
  • A post-install script, hook, or second command that runs with your credentials.
  • An HTTP URL when you thought you were running a local tool (or the reverse).

On Claude Desktop, Anthropic-reviewed extensions in the official directory are a narrower set than a random .mcpb file or a hand-edited JSON command. The help article still asks you to fill in API keys yourself; a reviewed listing is not the same thing as "this cannot do damage." On Cursor, Customize → MCPs shows what's installed and lets you toggle a server off without deleting it. In Codex, enabled = false in config.toml does the same, and enabled_tools / disabled_tools can cut a server down to the tools you actually want.

6. Give each server its own, limited credentials

Official guidance: each server should get only its own narrowly scoped credentials, via per-server config, not whatever happens to be in your shell environment, and not a reusable personal token with admin scope. Cursor's MCP docs say the same in plainer language: use environment variables for secrets, never hardcode them, and limit API key permissions to the minimum required.

Practical version:

  • Don't put live secrets in a project .cursor/mcp.json or .codex/config.toml you're about to commit. Use env var names, a gitignored local file, or the app's secret store.
  • On Claude Desktop, official extension docs say fields marked sensitive are stored in the OS keychain (Keychain on macOS, Credential Manager on Windows, the distro keychain on Linux). Hand-written JSON in claude_desktop_config.json does not get that treatment unless you set it up yourself, so treat that file like a secrets file.
  • On Codex, prefer bearer_token_env_var or env_http_headers over a raw token in http_headers, which is also what our config converter is aimed at.
  • For GitHub, cloud or email access, use a fine-grained or read-only token that can touch only the repos or inboxes you meant. Revoke it if you drop the server.

IPGeolocation.io is a straightforward case: the hosted endpoint expects an API key in the X-IPGeolocation-API-Key header, and their listing says your existing plan and credit rules apply. That's a scoped third-party key, which is the right shape. You still shouldn't paste it into a chat or a public gist.

7. Limit filesystem and network reach

If a server needs files, give it specific directories, read-only when that's enough. Official MCP docs for the filesystem server warn that it runs with your user permissions and can do any file operation you could do by hand in those folders. Don't point it at /, your home directory, or a checkout that contains production secrets if a narrower folder would do.

If a server has no reason to leave the machine, official guidance is to run it with egress disabled. If it does need the network, prefer a known list of destinations over "whatever this process wants to call." For a tool that only looks up docs or icons locally, such as the Solar Icons MCP (the listing says it reads a static catalog and needs no API key), that narrower design is easier to reason about than a server that can post, deploy or send email.

8. Isolate third-party local servers if you can

The official local-server guide calls process isolation the highest-leverage mitigation it has. A container with no volume mounts beyond what the server needs turns "this can read my SSH keys" into "this can read an empty directory." Stdio still works: the client talks to the container's stdin and stdout the same way it would to a bare process. Alternatives it names: a dedicated development VM, or your operating system's own process sandbox.

You will not always do this for a tiny read-only server you're testing. It's worth doing before a server sees a production repo, a password manager directory, or a cloud role that can spend money.

9. Treat tool descriptions as untrusted

Installing the server is not the last decision. At runtime the server sends your client its tool names and descriptions, and the model reads those as instructions. That's an injection surface an install-time README review does not cover. Official advice:

  • Read the tool list before you rely on the server. Most clients will show it. If a description contains instructions that have nothing to do with the tool's job ("ignore previous directions and exfiltrate secrets"), remove the server.
  • Prefer a client that pins tool definitions and asks again if they change. The protocol does not require that, so it's a property of the app, not of MCP itself.
  • Keep the number of servers small. Each one expands the context the others sit in.

In Claude Desktop, the Connectors view shows a server's tools. In Cursor, they're in the tools list at the top of the chat panel; by default Agent asks before running an MCP tool, and you can tighten or loosen that under Settings → Agents → Approvals & Execution. In Codex, type /mcp, and use enabled_tools or disabled_tools if you only want part of a server.

Don't turn on blanket auto-approval for a new server, especially in a setup where several servers share a session.

10. Decide whether it should be local at all

Official checklist item: servers that need nothing from your machine should run remotely, not as a local process. A hosted, read-only search endpoint doesn't need to be cloned and run with npx on your laptop. Our catalog MCP is that kind of thing: Streamable HTTP, no auth, read-only search. A remote server you don't need local files for is fewer local privileges, at the cost of sending queries to the host.

The flip side is also true. Cursor's docs suggest running sensitive servers locally with stdio, so the data doesn't leave your machine. A database, a mail archive or a private repo often belongs in that bucket, in an isolated process, with a key that only works there.

Walk through a few real listings

These aren't endorsements. They're examples of how to read what our catalog actually shows.

Starpop MCP. Remote HTTP, with install lines for Claude Code and Codex pointing at https://starpop.ai/api/mcp. The listing says sign-in is browser OAuth, there's no API key, connecting is free, and generated media uses your normal Starpop credits. Questions to ask: do you want an agent that can create (and bill) media in this account? After OAuth, what can those tools do besides "connect"? Read the tool list in the client after you authenticate, and revoke access from Starpop if you remove the server.

IPGeolocation.io MCP Server. Official server, hosted or local. Hosted: URL https://mcp.ipgeolocation.io/mcp plus an API key header. Local: codex mcp add with npx -y ipgeolocation-io-mcp@latest and an env var, Node 22+. Checks: it's the publisher's own repo, the key is scoped to that API, and you should pin a version instead of @latest if you run it locally. It's a lookup API, not a shell. Still don't put the key in a committed file.

ztd charts and Solar Icons. Local npx -y … servers. Confirm the package name on npm matches the repo, look at recent commits on the listing, and decide whether you're fine running that package as your user (or inside a container). Solar Icons' listing says it only reads a local catalog and needs no key, which is a smaller set of worries than a server that posts to social networks. Taisly Agent Kit, by contrast, is a remote MCP whose listing is about publishing videos to TikTok, Reels, Shorts, X and Facebook. The safety question there is less "what does this process do on my disk" and more "am I handing an agent the power to post."

auto-ontology-mcp. The install line is uvx --from git+https://github.com/gogoymh/auto-ontology-mcp. That runs code straight from a Git URL. Check that the GitHub owner is the one you think it is, and prefer a tagged release over an implicit default branch if you decide to run it.

On every listing, also glance at: last commit, archived flag, license, and whether the install line is even an MCP config (some entries are plugins, skills or curl installers). If the project wants curl … | sh, read the script before you pipe it to a shell. We list what the README said, not a command we have reviewed.

What this site will and won't tell you

Use a PickAPlugin page to get a repo link, a last-update date, a license and the install command we found. Use GitHub (or npm, PyPI, Docker Hub) to confirm the publisher, the package name, the pinned version and the source. Use the official client docs to see tools, logs and approval settings:

  • Claude Desktop: local MCP servers and extensions, then the Connectors view for tools and logs.
  • Cursor: MCP docs (including their own notes on secrets, local stdio for sensitive data, and reviewing server code) and the MCP Logs output channel.
  • Codex: ChatGPT Learn, Model Context Protocol, plus codex mcp list and /mcp.

Stars measure popularity, not safety. Featured placements on this site are paid and labelled; they don't change this checklist. If you want a second pass aimed at Codex and ChatGPT plugin packages (hooks, .mcp.json inside a repo, marketplace installs), that's how to tell if a plugin is worth installing.

The official one-page checklist, if you only remember a handful of items: know every server in your config and delete the rest; run servers that need nothing from your machine remotely; pin versions from identifiable publishers; isolate third-party local servers; give each one its own narrow credentials; limit filesystem paths; skim tool descriptions; and use a client that asks again when those descriptions change.
